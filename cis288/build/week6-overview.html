Week 6 — IAM Deep Dive

CIS 288 | Users, Groups, Roles, and Policies — Securing What You Built

For five weeks you've been building things in the cloud — VMs, storage buckets, networks. This week we answer the question that should be keeping you up at night: who is allowed to touch all of it? Identity and Access Management (IAM) is the security layer that every single cloud request passes through. AWS calls it IAM, Azure calls it Microsoft Entra ID, and Google calls it Cloud IAM — and as always with our three landlords, the concepts are identical and only the names change.

The Hotel Keycard Analogy

Think of your AWS account as a hotel. The root account is the master key that opens every door in the building — including the room where they keep the deed. You don't carry that key around; you lock it in the safe (enable MFA, never use it for daily work). Every employee gets their own keycard (an IAM user) that opens only the rooms their job requires. Housekeeping cards open guest rooms but not the office. The written access rules deciding which cards open which doors? Those are IAM policies — and in AWS, they're JSON documents. Visitors and contractors don't get permanent cards at all — they get temporary badges that expire (IAM roles). That one analogy is 90% of this week.

Users, Groups, and the Golden Rule

An IAM user is a permanent identity for a human — a console password, maybe access keys for the command line. A group is a collection of users that share a job function: Developers, Admins, ReadOnly. Here's the golden rule that separates professionals from people who create security incidents: attach policies to groups, never to individual users. New developer joins? Add them to the Developers group — done, they have everything they need. Developer moves to security? Pull them out of one group, drop them in another. Permissions stay clean, auditable, and reversible in one click.

Policies — The JSON That Decides Everything

Every policy statement has three required pieces: Effect (Allow or Deny), Action (which API calls, like s3:GetObject), and Resource (which things, written as an ARN). Two evaluation rules govern everything: default deny — if no policy explicitly allows a request, it's denied, period — and explicit deny always wins — if any policy says Deny, no Allow anywhere can override it. You never write rules for what's forbidden by default; you only open the specific doors people need. That principle has a name: least privilege, and it's the single most-tested IAM concept on every cloud certification exam.

Roles — Why Services Never Get Passwords

Your EC2 web server needs to read files from S3. The wrong answer — the one that ends up in breach reports — is creating a user, generating access keys, and pasting them into the code. The right answer is an IAM role: a temporary identity the EC2 service assumes at runtime. AWS hands the instance short-lived credentials that rotate automatically and never appear in your code, your config files, or your GitHub repo. If it's a human, it's a user in a group. If it's a service or an app, it's a role. No exceptions — and this exact pattern comes back next week when your Lambda functions need an execution role.

MFA and the Three Landlords

One stolen password should never equal a breach — that's what multi-factor authentication guarantees, and it goes on the root account before anything else. Across the landlords: AWS IAM users/groups/roles/policies map to Azure's Microsoft Entra ID with RBAC role assignments, and to Google's Cloud IAM with members, roles, and bindings. Azure scopes permissions down a hierarchy (subscription → resource group → resource); GCP binds them at the project level. Same hotel, same keycards — different front desks.
