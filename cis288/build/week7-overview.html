Week 7 — Serverless Computing

CIS 288 | Lambda, Azure Functions, and Cloud Functions — All Three Landlords

Here's a secret: "serverless" is a lie. There are absolutely servers — racks and racks of them. The difference is that you never see them, patch them, or pay for them while they're idle. You upload a function, pick what triggers it, and the cloud handles everything else. This week you'll deploy the exact same function on all three landlords — AWS Lambda, Azure Functions, and GCP Cloud Run functions — and judge for yourself which one makes it easiest.

The Vending Machine Analogy

Running an EC2 instance is like leasing a restaurant: rent is due 24/7, even at 3 AM when nobody's eating, and you handle the cleaning, repairs, and staffing. Serverless is a vending machine: you pay only when someone buys a snack. No purchase, no cost — and the machine owner handles restocking, power, and maintenance. Somebody presses a button (an HTTP request arrives, a file lands in S3, a timer fires) and the machine runs exactly once for that purchase. That button press has a name: a trigger.

Stateless, Scaled, and Occasionally Cold

Three properties define how serverless behaves. Stateless: every invocation starts fresh with no memory of the last run — anything worth remembering goes in S3, DynamoDB, or a database. Auto-scaling: one request runs one copy; a thousand simultaneous requests run a thousand copies, instantly, with zero load balancers to configure. Cold starts: the first call after idle time has to spin up a container, adding anywhere from 100 milliseconds to several seconds. Python and Node wake up fast; Java and .NET hit the snooze button. You'll measure a real cold start in this week's lab.

Anatomy of a Lambda Function

Every Lambda has four parts. The handler — the entry-point function that receives the trigger's event data as JSON. The runtime — your language environment (Python, Node, Java, Go...). Environment variables — configuration without code changes. And the execution role — straight out of Week 6: the IAM role your function assumes when it runs. Your function needs s3:GetObject? That permission goes on the execution role. Last week wasn't theoretical — it was the prerequisite.

Know the Limits (Before They Find You)

Lambda caps execution at 15 minutes — a 45-minute video render job dies at minute 15, full stop. Memory runs from 128 MB to 10 GB, and here's the counterintuitive part: CPU scales with memory, so a bigger function sometimes finishes so much faster that it's cheaper. Long-lived connections (think WebSockets), giant stateful apps, and databases don't belong in functions. Serverless is a brilliant tool — for the right jobs. Knowing which jobs is the skill.

The Three Landlords Sell the Same Machine

AWS Lambda (the 2014 pioneer), Azure Functions, and GCP Cloud Run functions are the same product wearing different uniforms: a handler, an HTTP/storage/timer trigger, a pay-per-execution bill, and a generous free tier (1M requests/month on AWS and Azure, 2M on GCP). The differences show up in the details — deploy speed, auth defaults, timeout ceilings — and this week's lab is built specifically so you experience those differences with your own hands.
